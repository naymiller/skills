# Как писать скиллы для агентов

Русская адаптация `writing-for-agents` из [mattpocock/skills](https://github.com/mattpocock/skills) (MIT, © 2026 Matt Pocock; текст лицензии — `LICENSE-writing-for-agents.txt`), дополненная опытом сборки плагина на 19 → 11 скиллов.

Цель текста для агента — одинаковый **процесс** при каждом запуске (не одинаковый результат). Ниже пять рычагов и порядок работы.

## 1. Указатель и две нагрузки

**Указатель** — строка, которая всегда в контексте и называет материал вне контекста плюс условие, когда за ним идти: `description` скилла, строка в таблице веток, ссылка на файл в CLAUDE.md. Срабатывание решает **формулировка указателя**, а не содержимое за ним.

- **Постоянная нагрузка** — всё, что висит в контексте каждый ход. Описания всех установленных скиллов — это она. Когда скиллов много (десятки из нескольких плагинов), описания хвоста списка обрезаются, и модель видит только имя — скилл перестаёт срабатывать сам. Поэтому скиллов меньше, описания короче.
- **Когнитивная нагрузка** — что человек должен помнить сам (какие скиллы есть и когда их звать). Тратим её только там, где нужен выбор человека.

Описание скилла (`description`):
- до ~300 знаков; первым — **ведущее слово** (что это);
- дальше **ветки**: по одному триггеру на ветку, 3–6 штук, например `Use when: «…», «…»`. Синонимы одной ветки — один триггер;
- без подробностей, которые есть в теле.

**Слияние вместо россыпи.** Три скилла одной темы (например: спрос, аналитика, чистка сайта) — один скилл с тремя ветками: одно описание вместо трёх. Отдельный скилл оправдан, когда у него своё ведущее слово, которое должно срабатывать само.

## 2. Лестница информации

Каждый кусок текста стоит на одной ступени:
1. **Шаг в файле** — что агент делает, по порядку.
2. **Справка в файле** — правила и факты, нужные каждой ветке.
3. **Вынесенная справка** — отдельный файл, до которого доходят по указателю, только на своей ветке.

Тест: что нужно **каждой** ветке — в `SKILL.md`; что нужно **некоторым** — в файл ветки (`<ветка>/PROCEDURE.md` или `references/…`). В `SKILL.md` слитого скилла — общий порядок, таблица «ситуация → файл» и общие правила. У файла ветки нет YAML-заголовка: иначе установщик может принять его за отдельный скилл.

**Рядом лежит связанное**: определение, правило и исключение — под одним заголовком. **Разрастание** (длинный файл без мусора) лечится выносом по веткам, а не сжатием слов.

## 3. Шаги и критерий готовности

Каждый шаг заканчивается строкой **«Готово, когда: …»**. Критерий:
- **проверяемый** — агент отличает «сделано» от «не сделано» (файл есть, скрипт вернул PASS, итог совпал с контрольным числом);
- **исчерпывающий** — «каждая страница проверена» сильнее, чем «проверь страницы».

Размытый критерий («разобрался») ведёт к **преждевременному завершению**: агента тянут видимые следующие шаги. Сначала уточни критерий; не выходит — вынеси следующие шаги за границу контекста (отдельный агент).

## 4. Ведущие слова и позитив

**Ведущее слово** — короткое понятие, которое модель уже знает (_пилот_, _песочница_, _сверка_, _бриф_). Повторяй его как слово, без пересказа: оно тянет за собой целое поведение. Три прилагательных в трёх местах — повод заменить их одним словом.

**Запрет притягивает запрещённое.** «Пиши комментарии в одну строку» работает лучше, чем «не пиши длинные комментарии». Формулируй, что делать.

**Исключение — жёсткие ограничения** (деньги, секреты, отправка, удаление, публикация, личные данные). Их оставляй явным запретом **и** ставь рядом позитивную цель: «отправка — после явного «да» с точным списком адресатов; без «да» письма не уходят». При переписывании в позитив проверяй, что запрет не ослаб: «берёшь публичные контакты» не равно «личные данные частных лиц не собираешь».

## 5. Чистка

- **Один источник правды.** Каждое правило — в одном месте; остальные ссылаются одной строкой. Жёсткое ограничение на собственное рискованное действие скилла остаётся в самом скилле, даже если общее правило есть в другом месте.
- **Окружение — тоже источник.** Не переписывай то, что агент узнает одной командой (`--help`, список файлов). Пиши то, чего не видно: договорённости, причину решения, **грабли**.
- **Пустые инструкции** (модель и так так делает: «будь внимателен») удаляй целиком.
- **Осадок** — устаревшие строки удаляй, а не копи; решение изменилось — правь все места, где жило старое.
- Факты, цифры, команды, пути и грабли — сохраняй: это опыт реальных случаев.

## Порядок правки существующего скилла

1. Сними метрики: длина каждого `description`, размер тел, число запретов, дубли между скиллами.
   Готово, когда: есть таблица «скилл → описание, тело, запреты».
2. Реши структуру: что слить в ветки, что оставить отдельным скиллом (по ведущему слову).
   Готово, когда: у каждого будущего скилла одно ведущее слово и список веток.
3. Перепиши по рычагам 1–5. Параллельно — карта правил: каждое правило старой версии → где оно теперь или почему удалено.
   Готово, когда: в карте нет строк без места или причины.
4. Независимая проверка: агент, который не видел правки, сравнивает старые и новые файлы и ищет потерянные и ослабленные правила (особенно жёсткие ограничения).
   Готово, когда: все находки «потеряно / ослаблено» исправлены.
5. Механика: YAML разбирается настоящим парсером, `name` = имя папки, закрывающий `---` на отдельной строке, все пути из текста существуют, имена файлов латиницей.
   Готово, когда: скрипт проверки и валидатор плагина проходят без ошибок.

## Бриф субагенту

Каждого агента запускай со свежим контекстом. В брифе: цель, входные пути и факты, точное правило с примером, ограничения, «Готово, когда», формат короткого отчёта. Секреты агенту не передаются; рискованные внешние действия (отправка, оплата, публикация) остаются у основной модели.
